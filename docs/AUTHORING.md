# Authoring

Guidance for anyone, human or agent, editing this repository. Students do not
need this file: theirs is `AGENTS.md` at the repository root. This one is for
people authoring the teaching material.

## What this repository is

The curriculum for **Titanium Engineer**, AI Aspire's five-day intensive for
enterprise engineers. Five days, about forty hours, in person, in groups of
four. Each group pitches a real problem from their own workplace on the first
morning and demos a working prototype on the last afternoon.

It is a content repository. The deliverable is teaching material, not an
application.

## The one idea that settles most arguments

**The course eats itself.** Every notebook runs on what the cohort produced
earlier. The prompts a group writes in the morning are the corpus they retrieve
over the next day. The transcripts they generate are what their judge scores.
The eval cases they write are what their agent is tested against. Nothing in
the exercises is a toy corpus about a fictional company.

So that every notebook still runs before the cohort has produced anything,
`data/seed/` holds a complete worked example: an internal IT helpdesk agent
called Deskmate, run through all five days by the instructors. `helpers.workspace`
reads the cohort's artifact when it exists and the seed when it does not.

## Rules for notebooks

1. **A notebook refers to itself and its own content, nothing else.** No day
   numbers, no module numbers, no "yesterday", no link to a sibling notebook.
   The test: would this sentence need editing if the modules were reordered?
   Name the artifact instead ("your transcripts", "the eval cases").
   Enforced by `scripts/nb_lint.py` rules P001 to P010.
2. **Read and write only through `helpers.workspace`.** Never open
   `workspace/` or `data/seed/` paths directly. Declare what the notebook
   reads and writes in its header cell, and write only what it declares.
3. **Run green two ways.** On an empty `workspace/` (the seed carries it) and
   on a full one. `make execute F=NN` proves both.
4. **Imports are earned.** Build the primitive from scratch in a few lines,
   then show the library and say in one line what it added.
5. **Weak then strong.** Show the bad version running, then the good one, on
   the same input.
6. **Claims are verified.** Before writing a version number, package name,
   keystroke, or API signature, check it. Students follow instructions
   literally.
7. **No consulting frame.** Students are engineers at the company they work
   for. No client framing, no engagements, no readouts.
8. **Never hand students a copy-pasteable solution to their own graded work.**
   Show shape, signature, or pseudocode.

## Imports

`helpers` is an installed package, declared in the root `pyproject.toml`. A
notebook imports it by name and adds nothing to `sys.path`. A path line has to
guess where the notebook is, and the guess differs between Jupyter, where the
working directory is the module folder, and marimo, where it is wherever the
student launched from. Both tools have to work.

The two modules with their own environment depend on the repository root as an
editable path dependency, so the same import works there.

## Format

The `.ipynb` is the source of truth. Edit it in Jupyter. The `.py` next to it
is a marimo mirror generated by `make marimo`; never hand-edit it. CI fails if
the mirror is stale.

Outputs are committed, because they are what makes a notebook readable on
GitHub. `make scrub` removes anything that must not be committed (keys, internal
endpoints, home paths, oversized cells). CI fails on an unscrubbed notebook.

### Interactive guides

Some notebooks are reading guides for interactive Claude Code. Their tasks use
conversation messages in place of code cells. Keep Learn, Create, Grow, the
original lessons, and student-owned questions. The student interprets evidence;
Claude may run the experiments described in the module README.

Put extracted algorithms in a separate `*_tools.py`. The Python file with the
notebook's name remains a generated marimo mirror. Keep real recorded results
with provenance, and label any omitted source text. Do not present model output
as a verified answer or fill the student's Your turn exercise.

Test the tools directly, including real runs and optional workspace saves.
`make execute` only renders these Markdown-only guides; it does not test their
experiments. Likewise, `make seed` does not regenerate their artifacts from
reading-guide cells. Use the documented experiment tools when regenerating
those artifacts. Workspace writes are explicit; seed fallback supports reading
and experimenting without a mandatory conversation-export workflow.

## Layout

```
NN_Module_Name/
├── README.md          what you will build, time, reads/writes, setup
├── <Name>.ipynb       the notebook (source of truth)
├── <Name>.py          generated marimo mirror
└── data/              module-local data only; never another module's
```

`00_Setup/` is unnumbered and survives any reorder. `project/` belongs to the
group. `docs/schedule/` is the only place that says "Day N".

Module numbers are global and run in day order. Moving a module across days is
a rename plus a schedule row; notebooks contain no numbers, so a renumber
touches zero notebook prose.

## Style

`docs/STYLE.md` is the rule book and `scripts/nb_lint.py` enforces it. Every
notebook is three acts after a short front matter: **Learn** (the idea, from
scratch, weak then strong), **Create** (the same thing on the group's own
artifacts, written to the workspace, ending in `## Your turn`), and **Grow**
(prototype to production, responsible controls, stretch prompts). That is AI
Aspire's Learn, Create, Grow model applied to a notebook, and the lint checks
the acts exist and are in order.

The short version of the prose rules: one idea per cell, under 120 words,
sentence-case headers, no exclamation marks, one bold span at most, an em dash
only in a task header, no emoji in headers. A checkpoint after every code cell
says what the student should see and when to stop.

## Brand

AI Aspire only. Former client and partner names, their logos, their links, and
their sample corpora must not appear anywhere in the repository; the lint's
B0xx rules list the strings. The client for a given cohort goes in
`cohort.toml` and nowhere else; `make banner` renders it.

## Commands

```bash
make setup          # uv sync, keeping optional groups already installed
make check          # what CI runs: lint, links, marimo drift, scrub check, seed, tests
make marimo         # regenerate the .py mirrors
make scrub          # remove outputs that must not be committed
make execute F=05   # run one module's notebook for real
make check-day D=2  # validate the workspace through day 2
make seed           # regenerate data/seed by running the notebooks
make banner         # render images/banner.svg from cohort.toml
```
